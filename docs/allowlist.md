# The allowlist — what belongs in the public core

nano-ops is built **from an allowlist**, never by flipping an existing private
repo's visibility: git history would retain the state and secrets that were once
committed to it. Every file here was chosen deliberately. This is the rule that
decides.

## The rule

**Mechanism is public. Identity, policy, and data are not.**

A file belongs in the public core if a stranger could clone it, fill in their
own `loops.toml`, and have it work for their estate. If a file only makes sense
for one operator — their name, their employer, their repos, their loops, their
standing orders — it belongs in the private fork.

## The invariant

Nothing from a live installation may land here:

| Never committed | Where it lives instead |
|---|---|
| `state/` in any form — cursor, pace, ledger, per-loop history, dashboard output | gitignored; runtime only |
| Secrets of any kind, including `state/secrets/slack-user-token` | a file under gitignored `state/`, never a value in a committed file |
| Channel ids, user ids, workspace ids | `loops.toml` `[hub]`, gitignored |
| A real `loops.toml` (real loops, real channel, real hosts) | gitignored; `loops.example.toml` is the committed documented form |
| Absolute personal paths (`/home/<user>/…`), hostnames, tailnet or LAN addresses | `loops.toml`, or resolved at runtime from `$HOME` / the repo root |
| Operator names, personas, agent-deck group names | `loops.toml` `[hub]`; code defaults to the neutral `"ops"` |
| Employer, product, repo and ticket-tracker names | the private fork |
| Ledger or history *content*, even as an example | invented examples only |

The check before any commit here is a grep audit for those patterns. It is not
enough for a file to look generic — a hardcoded session title or group name is
just as much one installation's identity as a channel id is.

## What is in, and why

| Component | Why it is core |
|---|---|
| `bin/ops` | the operator CLI. Identity comes from `loops.toml`; the always-on verbs wrap `flox services`, so it installs nothing outside the repo. |
| `bin/doorbell` | the responsiveness path. Generic poller; session to kick and profile come from config. |
| `bin/dashboard`, `bin/dashboard-refresh`, `bin/dashboard-server` | the estate view. Pure readers over `state/`; every label and filter reads from config. |
| `bin/usage-fetch` | the budget signal. Talks only to the model provider's own read-only usage endpoint. |
| `bin/followups` | the durable action-item store. Generic add/resolve/list over its own state dir. |
| `hub/` | the hub session's home and its tick skill — the control-plane mechanism. |
| `.flox/env/manifest.toml` | the toolchain and the always-on `[services]` declarations. |
| `loops.example.toml` | the registry's documented shape, with no real entries. |
| `docs/` | architecture, this allowlist, and the always-on runbook. |
| tests next to their scripts | they run against tempdirs, never real state. |

## What is deliberately out

- **The loops themselves.** A loop is where policy concentrates: which repos it
  watches, which org's conventions it enforces, which reviewers it pings. The
  *shape* of a loop is core (`loops/<name>/` = CLAUDE.md + skill + scripts +
  `state/<name>/`, registered in `loops.toml`); any particular loop is not.
  A generic example loop belongs here eventually; a working loop from a live
  estate does not.
- **Standing orders in the hub skill.** The hub skill carries the tick
  mechanism — classification, ledger, health pass, pacing. It does not carry
  rules like "auto-fix red CI on PRs authored by <username>" or "relay the
  morning brief", which name one operator's loops and accounts. Those stay in
  the private fork's copy of the skill.
- **`docs/lessons.md` and a populated `docs/ideas.md`.** Distilled from one
  estate's ledger; they read as a diary of that installation. `docs/ideas.md`
  exists here only as the empty file the hub appends to.
- **Machine-setup runbooks** naming particular hosts, drives, or accounts.
- **Installed systemd units.** The always-on supervisor is documented as a
  template in [`always-on.md`](always-on.md) and generated by the operator on
  their own machine; nothing here installs or touches a unit.

## Keeping it true

The private fork tracks this repo as `upstream` and rebases onto it. That only
stays sustainable while the split above holds: improvements to *mechanism* are
made here and flow down, and installation *policy* stays in the fork's own
commits. A mechanism fix made only in the fork becomes a permanent rebase
conflict — and an identity leaked into the core becomes permanent history.
